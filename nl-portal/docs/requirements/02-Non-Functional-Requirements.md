## 1. Purpose and standards alignment

This document makes the platform's quality requirements testable without adding unnecessary infrastructure. It uses ISO/IEC/IEEE 29148:2018-style requirement identification and verification, and ISO/IEC 25010:2023 as a product-quality coverage framework. ISO/IEC 25023:2016 informs measurement discipline; it does not supply project-specific numeric targets. Security review may use an agreed OWASP ASVS control profile; accessibility is the PRD's WCAG 2.1 AA requirement. ISO/IEC 27001:2022 is an organisational control reference, not a claim that this application or team is certified.

The quality coverage is functional suitability, performance efficiency, compatibility, interaction capability, reliability, security, maintainability, flexibility and safety. Functional correctness is specified primarily in the FR document; this document governs how it is verified and operated. No assertion of standards compliance is made without an approved assessment and evidence.

Each row defines an immutable ID, normative requirement, target and evidence, applicable delivery, source and accountable review role. All catalogue requirements are mandatory at their stated gate once approved. **Established** means a target/rule already in the PRD or repository instructions. **Proposed** means this document supplies a measurement convention or engineering control for approval. **Decision required** means the requirement cannot pass until the named decision is resolved; it is not permission to invent a value.

Sources: **PRD** = [PRD v4.0](../PRD-Noatum-Customer-Platform.md); **ROOT** = [repository rules](../../CLAUDE.md); **ADR** = the [architecture decisions](../adr/); **KICK** = [kickoff plan](../Project-Kickoff-and-Phase1-Plan.md); **SIMPL** = [simplification register](../Simplification-Register.md); **UC** and decision IDs are recorded in the [index](README.md). Delivery P1-P5 follows the [delivery plan](03-Phased-Delivery-Plan.md), not PRD priority labels. Tests shall reference NFR IDs and preserve their workload, environment, build and actual results.

## 3. Performance and capacity

### 3.1 Measurement contract

The PRD gives response budgets but does not define percentiles, concurrency, throughput, network profile or soak duration. This specification proposes **p95** for the interactive targets, measured under a signed workload profile, and requires p50/p95/p99 plus error rates to be reported. Percentile choice is not an existing PRD promise. Product and Engineering must approve D-07 before performance acceptance; the same profile shall be versioned with test evidence.

The profile must specify customer count, customer data distributions, concurrent active users, requests/second by journey, ingestion rate/burst size, payload sizes, test duration, database size/indexes, cache condition, client/device/network, Azure service sizes and enabled features. Server endpoint latency and browser journey timing are recorded separately. Background workloads run during representative interactive tests. Failed requests cannot be excluded to manufacture a passing latency result. Values outside the load generator's capacity invalidate the run.

Each release's quality report shall include requirement ID, approved target/profile, test method/tool, environment/build, dataset, actual result, evidence location, residual risk, owner and accept/reject decision. Empty targets and unsatisfied decision gates cannot be marked passed. Exceptions require an explicit bounded waiver and expiry from the accountable owner; no waiver may silently remove tenant, financial privacy, required approval or recorded publication-policy boundaries. Under UC-12, direct publication is an explicit admin policy, not a runtime waiver of failed CW1 confirmation.

Minimum pilot evidence: identity/tenant security review, per-entity isolation tests, permission-denial coverage including settings scopes, quote/configuration concurrency tests, direct-publication tests without a priced-offer CW1 job, and a real CW1 round trip for the CW1-confirmed path. Include a performance report, EN/ES and accessibility review, restore rehearsal covering policy history/published snapshots, operational alert/runbook demonstration, second-region configuration rehearsal and Product/Operations sign-off. A direct-only pilot cannot be used as evidence that CW1 integration passed; full Phase 1 acceptance retains both paths' evidence. The availability SLO begins being measured in production; a preproduction test does not prove a month's availability.
