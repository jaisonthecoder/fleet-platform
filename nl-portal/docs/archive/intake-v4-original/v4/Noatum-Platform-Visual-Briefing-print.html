Customer Information Platform

One portal where our customers see and do everything.

Track, quote, book, download, pay and get alerts — in one login, in the Noatum brand. The portal connects to the system our operations teams already use, so nothing is typed twice.

Today

  • Customer emails or calls to ask where cargo is
  • Quotes prepared by hand and sent as attachments
  • Documents and invoices requested one by one
  • Several disconnected tools with separate logins

With the portal

  • Customer sees every shipment and milestone live
  • Instant price where rates exist, or a request routed to the branch
  • Downloads documents and views invoices themselves
  • One login, one Noatum brand, in every country

How the platform works

Five layers. The customer works on the top one. Shipment updates come in and quote requests go out only through the bottom one.

Screens never decide

Whether a customer may see a shipment or accept a quote is decided in the business-rules layer and checked again there, whatever the screen shows.

Fast because the data is already here

Shipment lists and timelines open instantly because the portal holds its own copy. New milestones from operations refresh that copy as they happen.

One connection point, many adapters

Each outside system has its own adapter in the integration layer, and they all run inside one service. A new carrier feed or a different operations system later means a new adapter, not a new portal.

Phase by phase — for your confirmation

We start with one pilot customer in one region and add features in the order below. Each phase is complete and usable on its own. Please confirm the phases you agree with and mark anything you want changed.

Phase 1

Set-up and quotes

The customer can

  • Log in with their own users and roles
  • Request a quote for air, sea FCL or sea LCL
  • Get an instant price where we have rates, otherwise a priced quote from our team
  • Accept the quote and download it as a PDF

Behind it: customer set-up, data separation, connection to the operations system, Noatum brand.

Done when the pilot customer is quoting live
Phase 2

Tracking

The customer can

  • See every shipment, container and flight with live milestones
  • Download documents
  • View invoices and credit notes
  • Receive alerts for delays and customs holds
  • Run standard reports

Behind it: shipment data flowing in from the operations system; public track and trace page.

Done when the pilot customer tracks and downloads in the portal
Phase 3

Booking and claims

The customer can

  • Book from an accepted quote, or book directly
  • Upload their shipping documents
  • Pick a sailing
  • Raise a claim and follow it
  • Set their own email alert rules

Behind it: bookings created in the operations system; claims in Dynamics 365.

Done when a portal booking runs end to end
Phase 4

Insight

The customer can

  • See predicted arrival times
  • See CO2 per shipment; use the public CO2 calculator
  • Build their own reports; use Power BI dashboards
  • Ask the AI assistant

Behind it: prediction models, emissions engine, analytics store. Every automated figure can be checked and corrected by a person.

Done when predictions and analytics are live for pilot customers
Phase 5

Open up

The customer can

  • See purchase orders against shipments
  • Pull their data into their own systems
  • Use the portal in more languages

Behind it: public API, data feeds, more regions and customers, a second operations system if ever needed.

Done when a customer consumes our data directly

Start small

Every feature ships switched off and is turned on customer by customer. Adding the second customer or region is configuration, not a new project.

The CargoWise simulator

The portal needs to talk to our operations system, CargoWise One. Access to a test copy of it depends on another team. So we build a small stand-in first, develop and demo against it, and switch to the real system by changing a setting.

Our platform

Built and tested exactly as it will run in production

Simulator

Pretends to be the operations system. Development and testing only

Real operations system

Connected when access is granted. Same portal, new setting

It does

  • Accept our quote and booking messages and reply with prices and confirmations
  • Push fake shipments, milestones, documents and invoices
  • Hold a small test world of organisations, lanes and shared shipments

It is not

  • A copy of the operations system — no business logic
  • A second source of truth — switched off in production
  • Final until real sample messages are confirmed

It gives us

  • End-to-end demos before real access
  • Realistic tests for customer data separation
  • A permanent automated test environment

Application architecture

For the technical team. The portal is deliberately small: one web app, one service, one database. Microsoft Entra handles sign-in, so we write no login code. Background work runs as jobs inside the same service, queued in the same database, so there is no separate worker and no message broker to operate.

Application container (ours) Module, screen or store Run by another team or by Microsoft Data flow with protocol Development and test only

Deliberately small

One web app, one service, one database, plus file storage. No cache server, no message broker, no separate worker, and no login code of our own. Fewer moving parts means fewer things to operate and fewer places to fail.

Still flexible

Every outside system sits behind an adapter, jobs sit behind a queue interface, and the customer’s login method is a setting. A cache, a broker, a separate worker or a second transport system can be added later without touching the data model.

Safety is not simplified

Customer separation is enforced twice: by the data-access layer and by the database itself. Every request carries a permission check. Every automated value carries where it came from and can be corrected by a person.

Customer Information Platform — information and access requests

From the platform development team · 04.09.2026

Purpose. We are building a customer portal that reads shipment, document and invoice data from CargoWise One and sends customer quote requests and bookings back into it. We need the items below to build against an accurate test stand-in first, and connect to a real test instance later.

A. Needed now half a day

1. A named contact and a backupAnswers message-format questions within one working day.
2. Sample XML messages, anonymisedUniversalShipment (sea FCL and air), UniversalEvent, UniversalTransaction (invoice), eDoc, quote message if one exists.
3. Which element identifies each party on a shipmentLocal client, shipper, consignee, notify party, agent — and which one is "the customer" for invoicing. This decides who may see a shipment.
4. Export of the organisation listCode, name, country, branch, status, parent or related link. CSV to start; a scheduled feed later.
5. Event and milestone codesAir and sea, with descriptions, marking internal-only codes.
6. Charge codes and document typesIn use, with descriptions.
7. Status valuesFor quotes, bookings and shipments as CargoWise sends them.

B. Needed next before the first real connection

8. Is eAdapter licensed and enabledOn which instances (TEST, UAT, PROD), and who administers it.
9. Message types enabledOutbound: shipment, event, transaction, eDoc, quote. Inbound: quote request, booking.
10. How outbound messages are triggeredPushed on save, scheduled, or polled; delivery method (HTTPS, SFTP, queue).
11. Authentication for both directionsCertificates, credentials, IP allow-listing.
12. A TEST instance with seeded dataWe may send messages into it and see the result in CargoWise screens.
13. Where our portal reference can be storedAdditionalReference, custom field or note, so replies can be matched.
14. Source of instant quote pricesCargoWise rate management or an external engine; if CargoWise, how rates are queried in real time.
15. Daily volumesShipments, events, documents, invoices per day and peak hours.

C. Needed before the pilot go-live

16. Pilot customers' organisation codesAll offices and the owning Noatum branch.
17. Historical dataOne-time load of open shipments for pilot customers, or start from the connection date.
18. Change-control processHow we are told when fields, codes or triggers change.
19. Behaviour when our endpoint is unavailableRetry, queue or drop.
20. Who signs offThat a portal-created quote or booking is acceptable to operations.
