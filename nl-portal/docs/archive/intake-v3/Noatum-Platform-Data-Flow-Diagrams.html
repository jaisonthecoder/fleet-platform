2 · Customer onboarding — end to end

From a company existing in CargoWise to its first user on the dashboard. Linking is one audited action with a confirm dialog (a second-person approval can be added later, ADR-003).

sequenceDiagram
  autonumber
  actor CS as Noatum Customer Success
  participant UI as Noatum Admin UI
  participant API as platform-api
tenancy · admin
  participant DB as PostgreSQL
  participant SB as Job queue (pg-boss)
  participant WK as integration-worker
  participant CW as CargoWise (org export)
  participant EM as Email service
  actor CA as Customer Admin (Acme)
  participant ID as Entra External ID

  Note over WK,CW: Daily import (runs before onboarding)
  WK->>CW: fetch organisation list
  CW-->>WK: org code, name, country, branch, status
  WK->>DB: upsert master_org (hash change detection)

  CS->>UI: New customer: name, country, tier, email domains, login method
  UI->>API: POST /v1/admin/customer-groups
  API->>DB: insert customer_group (status onboarding), audit group.created
  API-->>UI: CustomerGroupDto

  CS->>UI: search "Acme"
  UI->>API: GET /v1/admin/cw1-organisations?q=acme
  API->>DB: trigram search master_org (+ linked group if any)
  API-->>UI: ACMEUK001, ACMEAE001 …
  CS->>UI: link ACMEUK001, ACMEAE001 + justification
  UI->>API: POST /v1/admin/customer-groups/:id/accounts ×2
  UI->>UI: confirm dialog: organisation, code, country, customer
  API->>DB: insert customer_account (org code unique, linked_by) · audit account.linked
  API-->>SB: visibility.reevaluate {orgCode, toGroup}
  SB-->>WK: consume
  WK->>DB: TenantResolver over existing shipments → shipment_visibility · invoices by addressee · unmapped_entity → mapped

  CS->>UI: invite first Customer Admin (name, email)
  UI->>API: POST /v1/admin/customer-groups/:id/invitations {role: customer_admin}
  API->>DB: domain check · insert user_invitation (token_hash, expires_at) · audit invitation.sent
  API-->>SB: email.send invitation
  SB-->>WK: consume
  WK->>EM: branded email with link /invite/
  EM-->>CA: email

  CA->>UI: open link
  UI->>API: GET /v1/invitations/:token
  API->>DB: invitation_by_token() → group name, inviter, status
  CA->>ID: sign in with MSAL (Entra External ID, invitation-only tenant)
  ID-->>UI: access token
  UI->>API: POST /v1/invitations/:token/accept (Bearer token)
  API->>DB: accept_invitation(): email match → insert user (idp subject, office) · user_role · invitation accepted
  API->>DB: evaluateActivation → customer_group.status = active
  API-->>UI: 200
  UI-->>CA: dashboard (empty widgets, news banner)

  Note over CA,API: Customer Admin now invites colleagues the same way (POST /v1/invitations) — Noatum is no longer involved

4 · Quote request — instant and manual paths

sequenceDiagram
  autonumber
  actor C as Customer (Quoting role)
  participant W as portal-web
  participant Q as platform-api · quotes
  participant RA as RateEngineAdapter (in API, sync)
  participant RE as Rate engine
  participant DB as PostgreSQL
  participant SB as Job queue (pg-boss)
  participant WK as worker · TmsQuoteAdapter
  participant CW as CargoWise One
  participant EM as Email / PDF

  C->>W: wizard: mode, route, cargo, services, refs (autosave)
  W->>Q: PATCH /v1/quotes/:id (draft)
  Q->>DB: quote, quote_version (status Draft)
  C->>W: Submit
  W->>Q: POST /v1/quotes/:id/submit
  Q->>DB: validate · chargeable weight · account org code chosen server-side · status Requested
  Q->>RA: price(request)  (25 s timeout, circuit breaker)
  RA->>RE: REST price request
  alt rates found
    RE-->>RA: options + charge lines + validity
    RA-->>Q: options
    Q->>DB: quote_option, quote_charge_line · status Quoted · notification
    Q-->>W: 200 Quoted (option cards)
  else no rate / timeout
    RA-->>Q: none
    Q->>DB: status In Progress
    Q-->>SB: quote.request {quoteId}
    SB-->>WK: consume
    WK->>CW: eAdapter inbound quote XML (org code, portal id in AdditionalReference)
    Note over CW: Branch pricing team prices in CW1
    CW-->>WK: outbound "quote priced" XML
    WK->>WK: match AdditionalReference · TenantResolver re-checks org code (quarantine on mismatch)
    WK->>DB: options + charge lines · status Quoted · notification
    Q-->>W: 202 In Progress (bell notifies when Quoted)
  end
  C->>W: Accept
  W->>Q: POST /v1/quotes/:id/accept
  Q->>DB: validity check · freeze version · status Accepted · audit
  Q-->>SB: quote.accepted · pdf.render
  SB-->>WK: consume
  WK->>CW: accept notification XML
  WK->>EM: render branded PDF → Blob · email "Quote accepted"
  Q-->>W: Accepted — ready to book

5 · Shipment update from CargoWise — ingestion, tenant resolution, alerting

sequenceDiagram
  autonumber
  participant CW as CargoWise One
  participant IN as platform-api · /integration/inbound
  participant SB as Job queue (pg-boss)
  participant WK as worker · TmsTrackingAdapter
  participant TR as TenantResolver
  participant DB as PostgreSQL
  participant AL as Alert engine
  participant EM as Email
  actor C as Customer

  CW->>IN: POST UniversalShipment / UniversalEvent XML (Loaded on board, MSKU1234567)
  IN->>DB: integration_message (received, source_message_id, correlation_id)
  IN-->>SB: cw1.inbound {messageId}
  IN-->>CW: 202 Accepted
  SB-->>WK: consume (idempotent on source_message_id + portal ref)
  WK->>WK: parse XML → canonical Shipment, TransportLeg, MilestoneEvent
  WK->>DB: mapping_event_code: CW1 code → canonical code, internal_flag
  WK->>TR: parties [(shipper ACMEUK001), (consignee BLUEQA001), (agent XYZ001)]
  TR->>DB: customer_account by org codes (active)
  TR-->>WK: grants [(Acme, shipper), (Blue Ocean, consignee)]  — agent ignored by policy
  WK->>DB: upsert shipment, shipment_party, legs, milestone_event (provenance)
  WK->>DB: replace shipment_visibility rows (same transaction) · audit visibility.granted
  alt no grants
    WK->>DB: unmapped_entity (open)
  end
  WK-->>SB: shipment.updated {shipmentId}
  SB-->>AL: consume
  AL->>DB: evaluate standard rules + subscriptions (ETA delta → potential delay)
  AL->>DB: notification rows for users of Acme and Blue Ocean
  AL-->>SB: email.send (subscribed users)
  SB-->>EM: send
  C->>C: timeline shows "Loaded on board, Shanghai" · bell count +1
Invoices (UniversalTransaction) follow the same path but resolve visibility from the addressee org code only, so Acme UK does not see an invoice addressed to Acme Dubai. Documents (eDocs) inherit the shipment's visibility and then apply the internal_only and restricted flags.

9 · State machines

Quote

stateDiagram-v2
  [*] --> Draft
  Draft --> Requested: submit
  Requested --> Quoted: rate found (instant)
  Requested --> InProgress: no rate → CW1
  InProgress --> Quoted: CW1 priced
  Quoted --> Accepted: accept (within validity)
  Quoted --> Rejected: reject with reason
  Rejected --> Requested: new version
  Quoted --> Expired: validity passed
  Draft --> Cancelled
  Requested --> Cancelled
  InProgress --> Cancelled
  Quoted --> Cancelled
  Accepted --> [*]: booked

Booking

stateDiagram-v2
  [*] --> Started
  Started --> Submitted: submit (complete)
  Submitted --> Confirmed: CW1 shipment ref
  Confirmed --> InTransit: departed (from events)
  InTransit --> Delivered: delivered
  Started --> Cancelled
  Submitted --> Cancelled: before milestone gate
  Confirmed --> Cancelled: before milestone gate
  Delivered --> [*]

Customer group

stateDiagram-v2
  [*] --> Onboarding
  Onboarding --> Active: ≥1 active account AND ≥1 Customer Admin accepted
  Active --> Suspended: suspend
  Suspended --> Active: reactivate
  Active --> Closed: close
  Suspended --> Closed: close
  Closed --> [*]

User and invitation

stateDiagram-v2
  state Invitation {
    [*] --> Pending
    Pending --> Accepted: link used, email matches
    Pending --> Expired: TTL passed
    Pending --> Revoked: admin revokes
  }
  state User {
    [*] --> ActiveU: invitation accepted
    ActiveU --> Locked: failed logins
    Locked --> ActiveU: timeout / admin unlock
    ActiveU --> Deactivated: admin
    Deactivated --> ActiveU: reactivate (re-auth)
    Deactivated --> Erased: retention passed (Phase 2)
  }
